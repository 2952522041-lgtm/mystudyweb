# 架构统筹与 Luna 协作开发

用户已授权在编码任务中采用此分工，无需为每次正常派发重复征求确认。主 Agent 保留当前模型并对最终结果负责；子 Agent 执行明确限定的基础编码任务。

## 任务分配

- 主 Agent 先检查仓库要求、已有改动和相关实现，确定问题、接口及验收条件，再分配任务。架构决策、跨模块集成、数据迁移、存储事务、权限边界及难以定位的并发问题由主 Agent 负责。
- 将独立、边界清楚的组件实现、样式调整、简单校验、适配代码、机械性重构及相关测试交给 Luna。任务小但风险高时，不按代码行数判断为基础任务。
- 只有子任务能够独立进行，且主 Agent 同时有架构、另一模块、集成准备或审查工作可做时才派发。单处文案修改、一次查询等微小任务直接完成，不为使用子 Agent 人为拆分。
- 根据当前工具实际公布的并发槽位调度；保留主 Agent 的槽位。不固定启动数量，不为占满槽位新增工作。

## 子 Agent 配置

使用当前环境的子 Agent 工具（例如 `collaboration.spawn_agent`），指定：

```json
{
  "task_name": "bounded_implementation",
  "model": "gpt-5.6-luna",
  "reasoning_effort": "max",
  "fork_turns": "none",
  "message": "填写本次任务、文件边界、接口约定、验收条件及相关仓库要求。"
}
```

- 明确传入模型和推理强度；此用户选择为 `gpt-5.6-luna` + `max`。不使用不存在的 `gpt6lunamaxfast`，也不声称开启了工具未提供的 `fast` 参数。
- 显式覆盖子 Agent 模型时使用 `fork_turns: "none"` 并提供自足的任务说明，避免全量继承导致模型覆盖失效，也避免发送无关对话或凭据。
- 派发前核对工具支持的模型与参数。如果该模型不可用或工具拒绝覆盖，说明限制，由主 Agent 继续处理；未经用户指示不静默替换子 Agent 模型，不以默认模型冒充 Luna。
- 不用创建用户可见新任务的工具代替内部子 Agent。子 Agent 不继续派生其他 Agent。

## 每次派发的任务说明

提供具体目标和必要上下文，并包含：

1. 允许修改的文件或目录，以及需要遵守的接口、类型和行为。
2. 验收用例、相关测试命令、适用的 AGENTS.md 要求。
3. 共享工作区约束：尊重已有改动，不覆盖其他人的工作；需要跨出边界时先向主 Agent 报告。
4. 交付内容：改动文件、实际测试命令和结果、未解决的问题。不将“应该通过”报告为已通过。

并行子任务尽量修改不同文件；共享接口由主 Agent 先确定。基础子任务不得自行扩大为架构重写、依赖升级或部署。共享工作区由主 Agent 统一执行 Git 提交，子 Agent 不自行提交、推送、安装或发布。

## 审查与交付

- 主 Agent 在子任务执行期间推进自己的工作，不重复实现同一个子任务。依赖出现变化时，及时更新或停止受影响的派发。
- 收到结果后审查实际 diff、调用方和测试，检查行为、边界条件及是否越界。不要仅凭子 Agent 的完成声明验收。
- 发现子任务覆盖用户改动或多个任务编辑同一处时，先暂停相关写入，由主 Agent 核对任务开始前的改动并处理具体差异；不要整文件回滚或覆盖来消除冲突。
- 发现问题时给出具体失败案例和修改范围，要求原子 Agent 修复；同一问题经过两轮明确反馈仍未解决，主 Agent 接手或重新缩小任务，避免无限返工。
- 集成后运行与改动相称的测试和仓库要求的全部检查。需要提交的仓库由主 Agent 在验证通过后提交；不得覆盖或混入用户无关改动。遵守项目要求的测试与提交规则。
- 区分源码修改、构建产物和已安装/部署版本。交付时准确说明验证和提交结果；只有实际安装或部署并核对后，才称已更新运行版本。

此技能改变开发分工，不扩大用户任务范围或外部操作授权。用户本次明确要求不使用子 Agent 或选择其他模型时，遵从本次要求。
